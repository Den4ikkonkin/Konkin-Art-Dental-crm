# Уведомления в Telegram

Утренняя сводка о назначенных пациентах приходит в Telegram. Записи берутся из
нарядов: время приёма — поле `appointment`, срок готовности — `due_on`.

## Что где лежит

| Файл | Назначение |
| --- | --- |
| `supabase/migrations/0002_notifications.sql` | Таблицы `notification_settings` и `notification_log` + RLS |
| `src/lib/digest.ts` | Сборка текста сводки. Общий для сайта и бота — превью и сообщение не расходятся |
| `src/lib/notifications.ts` | Чтение и запись настроек, журнала, тестовая отправка |
| `src/app/notifications/page.tsx` | Страница «Уведомления»: журнал, настройки, код привязки, превью |
| `src/app/api/telegram/test/route.ts` | POST — отправить сводку сейчас (ключ бота только на сервере) |
| `scripts/telegram-bot.ts` | Локальный воркер: long polling, команды, кнопки, планировщик |

## Настройка — 4 шага

### 1. Миграция базы

Supabase → SQL Editor → New query → вставить целиком
`supabase/migrations/0002_notifications.sql` → Run. Должно появиться
«Success. No rows returned». Файл можно запускать повторно.

### 2. Бот у @BotFather

Telegram → `@BotFather` → `/newbot` → имя и username → скопировать токен.
Добавить в `.env.local`:

```env
TELEGRAM_BOT_TOKEN=1234567890:AAH...
SUPABASE_EMAIL=ваша-почта@пример.ру
SUPABASE_PASSWORD=ваш-пароль
```

`SUPABASE_EMAIL` и `SUPABASE_PASSWORD` — та же учётная запись, под которой вы
входите на сайт. Воркер логинится через `signInWithPassword` и ходит в базу от
вашего имени: RLS пускает его только к вашим пациентам. Ключ `service_role`
намеренно не используется — он обходит все политики доступа, и держать его
на диске незачем. Сессия продлевается автоматически, поэтому сводка не упадёт
ночью, когда токен истечёт.

### 3. Привязка чата

```bash
npm run dev      # терминал 1 — сайт
npm run bot      # терминал 2 — бот
```

Открыть `http://localhost:3001/notifications` → «Получить код» → в Telegram
отправить боту `/start КОД`. Бот ответит «чат привязан», в журнале появится запись.

### 4. Проверка

На странице нажать «Проверить отправку» — сообщение придёт сразу же.
Дальше каждое утро в заданное время сводка приходит сама.

## Команды бота

| Команда | Действие |
| --- | --- |
| `/start КОД` | Привязать чат |
| `/today` | Приёмы на сегодня + кнопки «Готово» |
| `/tomorrow` | Приёмы на завтра |
| `/status` | Время, часовой пояс, состав сводки |

Кнопка «✓ Готово · №1001» ставит наряду статус `done` — сайт подхватит
изменение при обновлении страницы.

## Про время

`orders.appointment` хранит локальное время без часового пояса (`2026-10-20T09:30`).
Поэтому и «сегодня» считается в поясе лаборатории — по умолчанию **UTC+4 (Самара)**,
настраивается на странице. Сервер при этом может жить в UTC: сводка всё равно уйдёт
в 08:00 по Самаре.

Защита от двойной отправки — поле `notification_settings.last_sent_on`. Воркер
занимает дату перед отправкой, поэтому перезапуск в середине дня не пришлёт
сводку повторно.

## Если бот не отвечает

- `409 Conflict` в консоли — у бота остался webhook. Воркер снимает его сам
  при старте через `deleteWebhook`; если ошибка повторяется, проверьте, не запущен
  ли второй экземпляр `npm run bot`.
- «Код не подошёл» — код одноразовый, после привязки он стирается. Нажмите
  «Новый код» (прежняя привязка при этом сбрасывается).
- «Не задан TELEGRAM_BOT_TOKEN» — правьте `.env.local` и **перезапускайте**
  `npm run dev` и `npm run bot`: переменные читаются один раз при старте.
- Пустая сводка — проверьте, что у наряда заполнено поле «Приём» (дата и время),
  а не только срок готовности.

## Ограничения текущей версии

- Воркер работает, пока запущен `npm run bot`. Для круглосуточной работы он должен
  жить на постоянно включённой машине — домашний компьютер, мини-ПК или VPS
  с `pm2`/`systemd`.
- Webhook не используется: long polling выбран потому, что сайт запускается
  локально и публичного адреса для Telegram нет.
- Рассылка идёт всем привязанным чатам. При нескольких пользователях каждому
  придёт своя сводка — данные разделены по `user_id`.

## Telegram доступен только через VPN

Бот ходит в `api.telegram.org`, а он в России закрыт. Признак проблемы:
`✖ getMe: fetch failed` при запуске `npm run bot`.

Проверка сети:

```bash
npm run net
```

Скрипт по очереди проверяет прямой доступ, прокси и токен, затем пишет,
что именно сделать.

**Вариант A — VPN в режиме Global / TUN.** Тогда весь трафик Mac идёт через
туннель, и бот работает без настроек. Проверьте после включения: `npm run net`.
Режим «только браузер» или расширение в Chrome не подойдут — они не
покрывают терминал.

**Вариант B — указать прокси явно.** Node намеренно не читает системные
настройки прокси macOS, поэтому адрес нужно прописать в `.env.local`:

```env
TELEGRAM_PROXY=http://127.0.0.1:1087
```

Порт смотреть: Системные настройки → Сеть → ваше подключение → Подробнее →
Прокси. Часто встречаются 1087 (Surge), 7890 (Clash), 10808 (v2ray).
Поддерживаются схемы `http://` и `socks5://`.

Прокси применяется только к запросам Telegram. Supabase работает без него —
он доступен напрямую, и проксировать его не нужно.

## Бот сам находит системный прокси macOS

Встроенный в Node `fetch` не читает системные настройки прокси. Из-за этого
включённый VPN покрывает Safari и приложение Telegram, но не терминал —
и бот падает с `getMe: fetch failed` или бесконечным ожиданием.

Теперь бот читает настройки сам: вызывает `scutil --proxy` и берёт оттуда
адрес HTTP/HTTPS/SOCKS-прокси, если он включён в системе.

Порядок поиска:
1. `TELEGRAM_PROXY` из `.env.local` — ручное указание, главнее всего
2. системный прокси macOS
3. `HTTPS_PROXY` / `HTTP_PROXY` из окружения
4. если ничего нет — напрямую

Значит, если VPN клиент прописывает себя в системные настройки прокси,
бот заработает без всякой настройки.

Проверить, что видит система:

```bash
scutil --proxy
npm run net
```

Если `npm run net` пишет «Прокси не найден» и при этом первый пункт с
таймаутом — VPN работает как TUN, но не покрывает терминал, либо прокси
не системный. Тогда включите в VPN режим Global / TUN, либо узнайте
порт локального прокси и укажите его вручную в `TELEGRAM_PROXY`.
