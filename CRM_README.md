# Konkin Art Dental — CRM

CRM стоматологической лаборатории на Next.js 16, React 19, TypeScript и Supabase.
Техники ведут наряды, врачи работают с пациентами и материалами, администратор управляет системой.

## Что изменилось относительно исходного проекта

Исходный проект был рассчитан на одного пользователя: у каждой строки в базе был
`user_id`, а роли отсутствовали. Здесь добавлено разделение на роли, справочники
врачей и техников, шесть статусов наряда, бинарная оплата, передачи пациентов,
портфолио, прайс, настройки интерфейса, уведомления и рабочий ленточный журнал.

Точки правки остались прежними: модель — в `src/lib/model.ts`, доступ к данным —
в `src/lib/db.ts`, стили — в CSS-переменных темы.

## Структура

```
src/lib/model.ts          модели, zod-схемы, деньги, даты, цвета срочности
src/lib/roles.ts          роли, права, меню, очередь техника
src/lib/db.ts             единственное место общения с Supabase
src/lib/supabase.ts       клиент Supabase и бакет файлов
src/components/Shell.tsx  боковое меню и верхняя панель по роли
src/components/AuthGate.tsx           вход по логину
src/components/FirstLoginPassword.tsx обязательная смена пароля
src/app/api/admin/users/route.ts      создание учёток через service_role
supabase/migrations/                  миграции 0001–0011
supabase/tests/rls_check.sql          проверки RLS на тестовых учётках
tests/                                unit-тесты моделей и прав
```

## Порядок запуска миграций

Выполнять в Supabase → SQL Editor строго по номерам. Каждый файл идемпотентен,
повторный запуск безопасен.

| Файл | Что делает |
|---|---|
| `0001_init.sql` | базовые таблицы первой версии |
| `0002_notifications.sql` | настройки уведомлений Telegram (бот не трогаем) |
| `0003_archive.sql` | флаг архива у нарядов |
| `0004_db_size.sql` | служебная статистика размера |
| `0005_doctor.sql` | врач строкой в наряде |
| `0006_paid_on.sql` | дата оплаты |
| `0007_profiles.sql` | профили, роли, статусы, справочники врачей и техников |
| `0008_crm_entities.sql` | пациенты, связи, передачи, наряды, позиции, файлы, портфолио, прайс, настройки, уведомления, лента, папки Drive |
| `0009_rls.sql` | RLS-политики для всех таблиц |
| `0010_data_migration.sql` | перенос старых данных на Дениса, бинарная оплата |
| `0011_status_machine.sql` | машина статусов, начисление зарплаты, уведомления, лента |

Проверки прав:

```text
supabase/tests/rls_check.sql   — вставить целиком в SQL Editor → Run
```

Скрипт создаёт временные демо-учётки, проверяет четыре правила (чужой врач,
чужие зарплаты, архивный пользователь, администратор) и удаляет тестовые данные.

## Первый вход

1. Зайдите в Supabase → Authentication → Users, создайте первого пользователя
   с email вида `admin@konkin.local` и паролем не короче 8 символов.
2. В SQL Editor назначьте ему роль:

```sql
update public.profiles
set role = 'admin', login = 'admin', must_change_password = false
where user_id = (select id from auth.users where email = 'admin@konkin.local');
```

3. Войдите в приложение под логином `admin`.
4. Дальше учётки создаются в разделе «Пользователи»: логин, роль, временный пароль.
   Технический email пользователю не показывается и не требуется.

## Переменные окружения

```
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_ANON_KEY=
SUPABASE_SERVICE_ROLE_KEY=      только сервер, без префикса NEXT_PUBLIC_
GOOGLE_CLIENT_ID=
GOOGLE_CLIENT_SECRET=
GOOGLE_REFRESH_TOKEN=
CRON_SECRET=                    случайная строка не короче 32 символов
```

`SUPABASE_SERVICE_ROLE_KEY` нужен только маршруту `/api/admin/users` и бэкапу.
В браузер он не попадает.

## Проверки перед сдачей

```bash
npm run typecheck
npm test
npm run build
```

`npm test` запускает три набора: модель, годовой отчёт, роли и сроки.

## Правила, которые нельзя менять в интерфейсе

- Техник видит только свои наряды и свои архивные наряды.
- Врач не создаёт наряды и не меняет статусы.
- Врач не видит зарплаты техников.
- Архивный пользователь не входит в систему.
- Наряд в статусе «Готов» техник не правит — только отменяет готовность.
- Замена техника разрешена до статуса «Готов».
- Зарплата равна полной стоимости наряда и начисляется при переходе в «Готов».
- Отмена готовности обнуляет начисление до повторного «Готов».
- Существующие папки Google Drive и папку «3» система не трогает.
- Демо-данные не попадают в статистику, зарплаты, отчёты и выгрузки.

Все эти правила продублированы в `supabase/migrations/0009_rls.sql` и `0011_status_machine.sql`,
поэтому обход через прямой запрос к API не работает.
